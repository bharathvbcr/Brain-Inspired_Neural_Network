## 1. The single most important distinction

**The thing scoring 0.72 is not BINN.**

- `scripts/shd_calibration/` (python) and `binn-learn/src/shd_matched.rs` (rust) are the
  **matched SHD BPTT instrument**: a dense, single-hidden-layer LIF network
  (`w_in`, `w_out`, `b_out` — that is the entire parameter set), deliberately simple.
  Its job is to calibrate a gradient reference against an independent implementation.
- **BINN proper** is the event-driven graph engine: `binn-engine/` (timing-wheel event
  queue, multi-compartment cells, "work scales with events, not the idle cell
  population"), `binn-core/sparse.rs` (CSR/CSC connectivity), `binn-areas/`
  (assemblies, k-WTA, hubs, inhibition, predictive coding).

Every number in this campaign is about the *instrument*, not about BINN. Do not let a
writeup blur that.

Also independent: the **clean reference** (accuracy ≈ 0.939) is `Thvnvtos/SNN-delays`
(Hammouamri et al., ICLR 2024, learnable delays), cloned and pinned by
`reference.py:16`. It is a third-party SOTA baseline, not BINN and not the instrument.

## 6. Pitfalls — these will bite you

1. **Never move a registered threshold post-hoc.** `accuracy >= 0.80`
   (`model.py:284`) is registered: `SHD_INSTRUMENT_STATUS.md` §Why item 4, and the
   prereg's published table lists **e-prop at 0.808**. I initially recommended lowering
   it and was wrong. Amendments go in a **new timestamped file**, before the run.
2. **Hard threshold + float reassociation = non-reproducibility.** The spike function is
   discontinuous, so a one-ulp difference flips a spike and compounds through Adam over
   epochs. A BLAS matmul and a sequential `+=` are *not* interchangeable here. This is
   what broke Gate F. Fixture-level parity passing does **not** imply cell-level
   reproducibility — the parity fixture has atypically sparse frames.
3. **Do not touch `results/shd_instrument_v4/initialization/`.** The 216 rust cells are
   pinned to those bytes. `probe.py` writes longer order files to `probe/orders/` and
   asserts regenerated weights are byte-identical to the registered ones.
4. **Fold identities matter.** `TemporalAudit` derived `Default` gave
   `counts_preserved: false`, which is *absorbing* under the `&=` merge — every cell
   would have recorded a fabricated gate violation. Check the identity element of any
   accumulator you write.
5. **zsh specifics**: `python` is not on PATH — use `.venv-shd/bin/python`. zsh does not
   allow inline `#` comments by default; do not put them in commands you hand over.
6. **The rust binary is macOS arm64.** It cannot run in a Linux sandbox. `cargo` is not
   available there either — all rust verification must happen on the Mac.
7. **Sandbox limits**: ~3 GB RAM, so framing the full 8156/2264 split OOMs; background
   jobs are reaped between tool calls. Run long things in foreground batches or on the Mac.
8. **`--temporal` other than `intact` requires `--temporal-seed`**, and the binary must
   be rebuilt after any rust change — `probe.py readiness` checks for the flags and
   `convergence --run` now refuses to start if they are missing.

## 7. The novel result being chased

`PREREG_2026-08-02_SHD_TEMPORAL_INFORMATION.md`. The resolution invariance in §3 is the
signature of a **rate code**. Direct test: permute time bins, which preserves every
channel's spike count exactly and destroys temporal order.

Conditions: `intact`, `bin-shuffled` (order dies, within-bin synchrony survives),
`channel-shuffled` (order **and** cross-channel synchrony die), `reversed`. The
bin/channel contrast **decomposes order from synchrony** — most published shuffle
controls conflate them, and that is the genuinely novel part.

If order-invariance holds in the trained regime, 0.7151 is a **rate-code ceiling**,
which explains the resolution invariance and qualifies the recent claim that surrogate
gradients enable spike-timing learning (arXiv:2507.16043). That is a positive,
publishable result rather than a failed threshold.

**A capped pilot ran and is reported in prereg §2 as explicitly NOT evidence**: it
reached only ~0.31 accuracy, and an undertrained model has not learned timing, so
shuffling cannot take timing away from it. Gate 5.2 (intact ≥ 0.65) exists precisely so
that confound cannot recur.

**`l2_norm` — fixed, and worth reading as a pattern.** It accumulated squares in
f32, so a gradient with entries near 1e19 overflowed to an infinite norm while
every entry stayed individually finite — which is why the per-sample
`all_finite()` guard never caught it. The obvious fix, accumulating in f64
always, changes `mean_gradient_norm` in the last ulp for `ff+fixed` and breaks
Gate F against all 216 recorded cells.

It was avoidable. The overflow only occurs when the **sum of squares** exceeds
`f32::MAX` while the norm itself does not, so the f64 branch is reachable only
from values that were already infinite — and every recorded cell has a *finite*
`mean_gradient_norm`. Gating the widening on `!sum.is_finite()` leaves every
representable value bit-identical: **Gate F 13/13 PASS**. Registered in
`AMENDMENT_2026-08-03_L2_NORM_CONDITIONAL_WIDENING.md`.

The reusable rule: when a numerical fix looks like it requires invalidating a
recorded result, check whether the defect's domain and the record's domain
actually intersect. Here they are disjoint by construction.

**Why the bit-pin exists.** All 216 recorded cells are `ff+fixed`. `ff+alif`,
`rec+fixed` and `rec+alif` had no recorded output of any kind, so a shared-kernel
change could move them with every gate in the repository still green — the same
shape of hole that let the recurrent aliasing defect survive. Do not delete that
test to make a kernel change pass; re-pin it deliberately and say so.

**The Gate F double-hash is not paranoia.** The harness hashed the binary only
after the last cell, so a `cargo build` during a 5-minute sweep would have
recorded the new hash against results produced by two different kernels. That is
the exact provenance confusion the gate exists to detect.

   - **Revert the kernel work** to restore the original fingerprint. Costs the
     2.8× speedup and reinstates the recurrent-arm defect.
   - **Re-freeze** by deleting `manifest.json`. **Do not do this** — it silently
     destroys the record of what produced the 296 completed cells, and is
     unrecoverable. It is called out here because it is the path of least
     resistance and an agent under time pressure will otherwise take it.

6. **Three instrument defects, and a recurrent arm that learns but excurses.**
   Full write-up in `MEASUREMENT_2026-08-03_RECURRENT_ARM_STABILITY.md`; read its
   §3.5 and §4b first, because the earlier sections were revised against later
   data and the early reading was too alarming.

   **The defects are the durable part.** `non_finite_events` was declared, read
   by the pass predicate, written into all 296 cells — and **never incremented**,
   so `scientific = ... && non_finite_events == 0` was vacuous and the
   instrument's only numerical guard had never fired. `json_f64` wrote `inf`,
   which is not valid JSON, so a diverging cell produced a file nothing could
   read. Both fixed. A third — `l2_norm` accumulating in f32, so entries near
   1e19 overflow while each is individually finite — is **also fixed**, by
   widening to f64 *only* when the f32 sum is non-finite. That branch is
   reachable only from values that were already infinite, and every recorded
   cell has a finite `mean_gradient_norm`, so nothing registered moves: Gate F
   13/13 PASS. See `AMENDMENT_2026-08-03_L2_NORM_CONDITIONAL_WIDENING.md`.
   It corrects the *record*, not the dynamics — the two aborting h512 seeds are
   unaffected.

   **The science, corrected.** At h128/e20 both recurrent arms learn:
   `rec+fixed` 0.2633, `rec+alif` 0.3785, both with monotonically falling loss.
   `rec+fixed`'s gradient goes infinite in epoch 3 and then settles to ~1.8e2 for
   the remaining seventeen. Earlier 3-epoch cells looked catastrophic because
   **e3 sits entirely inside that transient**.

   **Then width changed the picture again — this is the part that matters, and
   it is replicated.** At **h512**, the width RECALIF registers, `rec+alif` at
   e20 across three seeds: 5170001 completes with a peak gradient norm of
   **7.36e29**; 5170002 **aborts** at step 220; 5170003 **aborts** at step 50. **Zero of three seeds produce a usable cell.** h128 and h256 are
   entirely clean (0/640) on the same configuration, so it is a property of the
   width, not of a draw.

   The completing cell **looks healthy** — loss falls monotonically to the lowest
   value measured anywhere, accuracy 0.3507. Nothing a reader would check flags
   it, which is exactly why the vacuous `non_finite_events` counter mattered:
   before today it would have read 0.

   **`PREREG_2026-08-02_SHD_BPTT_CEILING_RECALIF` cannot run as registered.** Its
   24 cells are `rec+alif` at h512. This is a blocking result about the
   instrument at that width, not a finding about recurrence — do not write it up
   as one. It called for a numerical fix; **clipping has since been tried and
   cannot work** — the abort fires on a per-sample gradient, strictly before
   the batch gradient clipping would act on exists. See
   `MEASUREMENT_2026-08-03_GRADIENT_CLIPPING_DOES_NOT_FIX_H512.md` §2. The
   remaining candidates are truncated BPTT or a narrower width, both
   registered in advance.

   Two things need a decision:
   - **A gradient-sanity validity gate — but not a magnitude threshold.** Every
     bound tried misclassifies a measured cell: `> 1e4` on the peak voids
     `rec+fixed` e20, which recovers and learns; the same rule restricted to the
     final quarter of epochs voids `rec+alif` e20, the best cell measured. §5 of
     the measurement now proposes only the safe part (void on abort, or on
     `non_finite_events > 0` with a non-falling loss) and says plainly that the
     real bound cannot be set from this data.
   - **What to do instead of rescaling `W_rec`.** The §5.6 pilot has now been
     run (`scripts/w_rec_scale_pilot.py`, 10 cells, scales 1.0 → 0.05) and
     **rescaling does not fix it**: the response is non-monotonic across three
     orders of magnitude, 8 of 10 cells exceed a peak gradient norm of 1e4, and
     `rec+alif` is worst at the *smallest* scale tested. Do not spend more time
     on the scale axis without a reason; the likelier lever is gradient
     clipping, which the training loop does not have. Full table in §3.2 of the
     measurement.

     The flag itself was worth adding — the initialiser had hard-coded the scale
     under a comment saying the registered value "is set by the G8 pilot, not
     here", so the pilot the prereg asks for could not be run at all.
     `init --w-rec-scale` defaults to 1.0 and reproduces every existing file
     byte-for-byte.

   This matters most for `PREREG_2026-08-02_SHD_BPTT_CEILING_RECALIF`, which
   exists to measure a **ceiling** for the recurrent arm. A ceiling depressed by
   gradient explosion would read as a finding about recurrence.

7. **The recurrent arms are now affordable.** 6.3x on recurrent training cells,
   bit-identical, registered in
   `AMENDMENT_2026-08-03_RECURRENT_KERNEL_TRANSPOSE_AND_SPARSITY.md`. The
   recurrent arms went from 21x slower than feed-forward to ~2.3x. This is what
   made decision 6 cheap enough to discover.

## 11. Working style that fits this repo

This codebase has a genuine preregistration culture — registered thresholds, validity
gates that dominate hypotheses, degeneracy flags, `INVALID_HARNESS` verdicts that may not
be cited as positive evidence, and a claim-axis header on every result document
(`CLAIM_AXIS.md`). Match it. Concretely: read the registered protocol *before* proposing
a change to it, put manipulation checks in code rather than in prose, and when a result
is not supported, say so in the document rather than softening the wording.
